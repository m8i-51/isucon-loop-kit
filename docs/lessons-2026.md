## 運用（AI に毎回守らせる）

- ベンチは enqueue したら完了まで点を追う。投げっぱなし禁止。
- 判定は **cold 1本目を信じない**。デプロイ直後は低く出やすいので warm 2本（または同等）で見る。
- 上がった構成の **古いスナップショットを再デプロイしない**。正は「今の best ソース／バイナリ」だけ。
- 大きな構成変更のあとは再起動試験。ディスク上に残るもの（unit・env・DB・バイナリ）だけが提出物。
- 良い点のあとに冷たいベンチを最後にしない。最終は warm で止める。
- QA で OK が出た施策は勝手にやってよい。禁止事項はレギュ／Clar を更新するたびにこのファイルと `ansible/AGENTS.md` へ追記。

## 計測の型（Go 前提）

- 先に **どこで時間が消えているか** を分ける: app CPU / DB CPU / ロック待ち / ネットワーク往復。感覚で全面書き換えしない。
- Go: `pprof`（CPU・必要なら mutex/block）。比率（例: JPEG 検証 vs 署名 vs その他）を書いてから触る。
- DB: `pg_stat_statements` / ロック待ちのブロッカー元。N+1 と「他人の行を握る Tx」を優先。
- 指標は生スコアだけにしない。人数・エラー率・1秒超比率など、伸びの因果に近いものを残す。
- 盲点: 1台だけ pprof を見て他台を見ない。proxy や役割分割したら **役割ごと** に取る。

## Go で効きやすかった型

- **検証パスの短縮**: 画素まで要らないなら逆 DCT 省略・ヘッダのみ・結果メモ化（`maphash` 等）。必ず等価テストしてから載せる。
- **署名・HMAC**: 応答パスから外す（アップロード時計算・バケット化キャッシュ）。`singleflight` はミスキーが極端に多いと効かない。
- **キャッシュは初期化で全消し**: リージョン横断の読み取り一貫性が必要な問題では、非同期複製キャッシュは危険。書き込み成功後の即反映が必須なら触らない。
- **UUID**: 時刻順が効くなら v7 相当（B-tree・通知など）。
- **検索**: メモリ一覧 + 版番号／指紋で取り直し判定。
- **SQL**: `JOIN LATERAL … LIMIT 1` など「1件ほしい結合」の見直し。索引の列順は実クエリの WHERE/ORDER に合わせる。
- **BYTEA / TOAST**: 大きなバイナリ列は `STORAGE EXTERNAL` 等で圧縮試行を避けると INSERT が落ちることがある（Postgres）。
- **環境変数化**: ポート・DB プールサイズは最初から env に出しておく（再ビルドなしで触れる）。

## Postgres / インフラで効きやすかった型

- 外部キーや autovacuum がクリティカルパス（投稿窓開始など）を食っているなら、レギュ内で外す／緩める判断を計測付きで。
- `TRUNCATE` がベンチ中に噛むなら延期・DELETE・切替を検討（仕様を壊さない範囲）。
- 複数台: **全面 proxy は CPU 奪い合いで沈みやすい**。GET のみ／役割分割など細い面から。
- CPUQuota や pool サイズは実測で合わせる。感覚の半分にすると逆に沈むことがある。

## やって FAIL / 即撤回したこと（再犯禁止）

- 署名の iterations を変える／画像 URL の署名形式・検証結果を変える。
- ユーザー横断の共有署名キャッシュ（他人の鍵で署名が見える系）。
- 有効期限の **切り上げ**（切り捨ては問題による。必ず小さな実験で切り分ける）。
- ルータ／運営が禁じた IP・ポートへの到達（Clar で失格になりうる）。
- envcheck / 運営モニタの改変・削除。
- 「速そう」な全面転送を、切り戻し条件なしで一気に当てる。

## AI への渡し方

1. 変更は git の branch / SHA で渡す。
2. デプロイは `ansible/playbooks/deploy.yml` だけ（`isuctl deploy` 禁止）。
3. 直後に `check.yml` → warm ベンチ → 点と主要指標を報告。
4. 仮説は **1つずつ**。同時に魔改造を重ねない。
5. 禁止リストはこのファイル + 当年のレギュ追記。
