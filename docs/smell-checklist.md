# 匂いチェック

毎手では埋めない。ベストの点がおよそ30分動いていないときだけ読む観点である。厚い手順を常時の門にしない。

観点は固定の全量ではない。ある回で効いて、別の回では出なかった手から足す。問題の名前は書かない。

アクセスログ、slow、ロック待ちは、その年のスタック（Web と DB）に合わせて読む。観点の名前はスタックに依存しない。

結果は [`docs/dayof/plateau-ledger.md`](dayof/plateau-ledger.md) に残す。各観点は 却下 / 採用 / 未着手。

## N+1

その文の calls と、対応するリクエスト本数。calls がリクエスト本数に対して積んでいないか。

## ロック待ち

その年の DB で見える待ちと、握っている側。

## 契約違反の匂い

[`docs/lessons-2026.md`](lessons-2026.md) の「やって FAIL / 即撤回したこと」を当年分として照合する。当たるものがあるか。

## cold / warm

判定は warm（2本目、または同等）で見る。cold は並べて記録する。

## ベンチ側の振る舞い

重いリクエストをベンチが途中で落としていないか。キャッシュを示す応答ヘッダで、同じ取得の繰り返しが止まっていないか。

## ホストの外の上限

アプリの外が頭打ちでないか。ベンチが応答を待ってから次を出すのか、決めたペースで出し続けるのか。負荷のパラメータを、仕様の範囲でもう一度探したか。

## アプリの中の層

計算、待ち、入出力を分けて測ったか。外側の合計時間だけで止めていないか。

## 台ごとの差と役割

台ごとの差を見て、役割の置き方に反映したか。一台の計測を全体の結論にしていないか。
